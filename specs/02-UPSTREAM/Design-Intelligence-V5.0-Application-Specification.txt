# Design Intelligence V5.0 Application Specification

## ARSO V2.2.1 Reference Application Edition

### AI-Native Fashion Design Intelligence：从业务语义、设计决策到视觉实例、诊断优化与企业知识演化的完整应用规范

这份文档不再把 DI-B01–B08 机械拼接，而是按照刚完成的 **Cross-Spec Consistency Freeze** 重新统一对象、版本、血缘和反馈闭环。

其中有两条上游约束尤其重要：

1. ARSO 将 Design / Fashion 视为 **multimodal + set-valued + preference-sensitive** 的代表性 Domain，并明确当前能声称的是 `Representational Compatibility`，不能因为框架能表达 Design Intelligence 就声称已经证明跨域优化能力。

$$

BusinessIntent
\rightarrow
DesignSemantics
\rightarrow
ExecutableDesign
\rightarrow
VisualEvidence
\rightarrow
Diagnosis
\rightarrow
ControlledImprovement
\rightarrow
GovernedLearning
}
$$

# Part III｜为什么叫 Design Intelligence

传统生成流程通常是：

$$

\rightarrow

$$

DI V5.0 则要求：

$$
\boxed{
StyleBrief
\rightarrow
DesignDecision
\rightarrow
DesignRoute
\rightarrow
DesignSpec
\rightarrow
Generation
\rightarrow
Verification
}
$$

其本质区别在于：

> Prompt 不再承担“全部设计思想”。

Prompt 只是：

$$
\boxed{
ExecutionArtifact
}
$$

而真正稳定、可积累、可编辑和可验证的资产是：

```text
Brief
Decision
Route
Spec

Grammar
Parameter Space
```

这与 ARSO 的基本原则一致：实例级 semantic decision 与具体 executor lowering 必须解耦。ARSO 上游规范也明确要求 `DecisionIR ≠ Prompt`，并把 Compiler / Executor 分离。

# Part IV｜Design Intelligence 的任务几何

这是理解 DI 与普通 benchmark 最大差异的地方。

Design Intelligence 通常不是：

$$
x\rightarrow y^*
$$

其中只有唯一正确答案。

而更接近：

$$
\boxed{
\mathcal D(B)
=
\{
d:
d\models B
\}
}
$$

其中：

* \(B\)：StyleBrief；
* \(d\)：一个设计实例；
* \(\mathcal D(B)\)：满足 Brief 的可接受设计集合。

因此它主要属于：

```text
Set-Valued
+
Constraint
+
Preference
+
Mixed Evaluation
```

而不是纯粹 Point Target。

这也是为什么：

$$
\boxed{
Different
\neq
Wrong
}
$$

以及：

$$
\boxed{
SimilarToReference
\neq
GoodDesign
}
$$

# Part V｜Reverse 与 Forward 两种工作模式

## 1. Reverse Design Intelligence

存在参考 Ground Truth / Target：

$$
Reference
\rightarrow
ObservedFeatures
\rightarrow
Spec
\rightarrow
Route
\rightarrow
Decision
\rightarrow
Brief
$$

再执行：

$$
Spec
\rightarrow
Generation
\rightarrow
Comparison
$$

主要目标：

```text
semantic reconstruction
representation completeness
compiler fidelity
generation fidelity
```

---

## 2. Forward Design Intelligence

没有唯一 GT：

$$
Trend
\rightarrow
Opportunity
\rightarrow
Planning
\rightarrow
StyleBrief
\rightarrow
MultipleValidDesigns
$$

目标不是：

> 生成“标准答案”。

而是：

$$
\boxed{
SatisfyBrief
+
DesignCoherence
+
CommercialFit
+
ControlledNovelty
}
$$

---

## 3. 两者不能混淆

Reverse 可以测：

```text
Target Fidelity
```

Forward 更重要的是：

```text
Brief Satisfaction
Constraint Satisfaction
Design Quality
Preference
Portfolio Diversity
```

因此不能使用：

> “与 GT 越像越好”

统一评价所有 Design Intelligence 任务。

# Part IX｜B01：Business Semantic State

B01 回答的是：

> 设计任务到底是什么，以及设计师决定了什么？

核心链：

$$
\boxed{
StyleBrief
\rightarrow
DesignDecision
\rightarrow
DesignRoute
\rightarrow
DesignSpec
}
$$

---

# 1. StyleBrief

StyleBrief 不是一段 prompt。

它是：

$$
\boxed{
Planning\rightarrow Design
}
$$

的正式业务协议。

至少应表达：

```text
Category
Customer
Market / Channel

Season / Occasion

Commercial Role

Price / Positioning

Style Intent
Mood / Aesthetic

Functional Requirements

Design Focus

Must Have
Must Avoid

Reference Intent

Material Context

Fit / Silhouette Direction

Novelty Expectation

Hard / Soft Constraints
```

---

# 2. Must / Prefer / Explore

所有要求不得压成一个权重。

正式分：

```text
MUST
PREFER
EXPLORE
AVOID
FORBID
```

其中：

$$
MUST
$$

属于约束。

而：

$$
PREFER
$$

属于偏好。

因此：

$$
\boxed{
Constraint
\neq
Preference
}
$$

---

# 3. DesignDecision

DesignDecision 回答：

> 为满足 Brief，这个设计要把有限的设计资源放在哪里？

例如：

```text
Primary Focus
Secondary Focus

Visual Hierarchy

Silhouette Strategy

Volume Distribution

Construction Emphasis

Surface Complexity

Material Expression

Novelty Allocation

Commercial Risk Allocation
```

它不是：

```text
Detailed Garment Description
```

而是：

$$
\boxed{
DesignStrategy
}
$$

---

# 4. DesignRoute

Route 是：

> 在同一个 DesignDecision 下，一条机制上可区分的实现路径。

例如同一个 Brief：

```text
Romantic summer mini dress
primary focus = waist
```

可以产生：

### Route A

```text
gathered waist
+
soft sleeve
+
clean skirt
```

### Route B

```text
corset-informed waist
+
minimal sleeve
+
panelled skirt
```

### Route C

```text
smocked waist
+
flutter sleeve
+
layered hem
```

所以：

$$
\boxed{
Route
\neq
RandomVariant
}
$$

---

# 5. DesignSpec

DesignSpec 是：

> 某个被选 Route 下，具有权威性的结构化设计意图。

正式取消：

> DesignSpec = Fashion Truth

这种过强措辞。

正确关系：

$$
\boxed{
DesignSpec
=
AuthoritativeStructuredIntent
}
$$

而不是：

$$
GlobalGroundTruth
$$

# 8. Design Grammar

Grammar 回答：


# 9. Semantic Parameter Space

从：


例如：

```yaml

  range:
    - minimal
    - low
    - medium
    - high
    - extreme

  body_region: upper_arm
  interactions:
    - silhouette
    - shoulder_structure
    - material_behavior
```

# 13. CompilerMappingTrace

这是 DI 中非常重要的可诊断资产。

必须记录：



# Part XII｜B04：Structured Evaluation

B04 不允许只有：


\boxed{

\neq

# 14. 两个最重要的 Objective

必须始终分开：

$$
\boxed{
DesignQuality
\neq
GenerationFidelity
}
$$

### Design Quality

> 这个设计想法是否好？

---

# 15. 为什么必须分开

可能：

```text
Bad Spec
+
Perfect Generation
```

即：

```text
Fidelity = High
Quality = Low
```

也可能：

```text
Excellent Spec
+
Poor Image Model Execution
```

即：

```text
Design Intent Quality = High
Fidelity = Low
```

如果混在一起，B05 无法正确诊断。

# Part XIII｜B05：Evidence-Bounded Diagnosis

B05 不回答：

> Critic 觉得哪里不好？

而回答：

> 在当前可观察证据下，我们有多大理由怀疑哪一个环节出了问题？

正式链：

$$
\boxed{

\rightarrow
Evidence
\rightarrow
DiagnosticBelief
\rightarrow
Hypothesis
\rightarrow
Probe
}
$$

---

# 18. DI Failure Loci

可以映射 ARSO R0–R9，但 DI 应提供领域扩展：

```text
Brief / Objective

Context / Reference

Fashion Semantic Model

DesignDecision

DesignRoute

DesignSpec

Compiler

Executor

Evaluator

Environment / Runtime
```

---

# 19. DiagnosticBelief

不应输出：

> Root cause = Compiler。

而应允许：

```text
Compiler        0.48
DesignSpec      0.27
Executor        0.19
Unknown         0.06
```

这里只表示：

$$
EvidenceConditionedBelief
$$

不是严格统计 posterior，也不是因果真理。

---

# 20. DiagnosticHypothesis

每个 hypothesis 必须至少包含：

```text
Locus

Mechanism

Scope

Expected Observation

Predicted Effect

Falsifier

Required Probe
```

例如：

> 当前 Waist detail 的视觉缺失并非 DesignSpec 缺失，而可能由 compiler 将 localized gathering 降格为 generic waist emphasis 导致。

然后才设计 Probe。

---

# 21. Probe

例如：

```text
Freeze Spec
+
replace Compiler
```

或：

```text
Freeze Compiler
+
replace Executor
```

从而主动区分相邻解释。

所以：

$$
\boxed{
ProbeAsks
}
$$

而：

$$
\boxed{
InterventionChanges
}
$$

# 25. Intervention ≠ Deployment

必须继承 ARSO：

所以：



> **Design Intelligence V5.0 是 ARSO V2.2.1 在开放式、多模态、集合值服装设计任务上的 Reference Application。它以 StyleBrief 作为商品企划向设计阶段的显式任务合同，通过 DesignDecision 分配设计关注与复杂度，通过多条 DesignRoute 表达满足同一 Brief 的不同设计机制，并由 DesignSpec 形成可版本化、可编辑、与执行器无关的权威设计意图。Fashion Ontology、Design Grammar 与 Semantic Parameter Space 提供稳定领域语言，但企业偏好与全局 Fashion Knowledge 被严格区分。Generation Compiler 将 DesignSpec lowering 为不同图像模型、编辑模型及未来 CAD/Simulation Executor 的 GenerationPackage，并通过 CompilerMappingTrace 保留语义到执行的映射证据。B04 将 Design Quality、Brief Fidelity、Constraint Satisfaction 与 Generation Fidelity 等 Objective 与具体 Evaluator 解耦；B05 根据真实运行 Trace、Measurement 与 Contrastive/Counterfactual Evidence 在可观察性边界内维护 DiagnosticBelief 和可证伪 Hypothesis；B06 仅对被怀疑的系统资产执行最低充分的受控 Intervention，并通过 sandbox、target、regression 和 generalization validation 验证修改。B07 以 immutable DesignStateRevision、Edit、Fork、Merge、HumanDecision 和 DesignLineage 支持真实设计师—AI 协作，而不会夺取 B01 的 semantic ownership。B08 将全部运行结果首先视为 History，只把经过 curation 的内容转为 Memory，并要求任何 Brand Preference、Enterprise Knowledge、Repair Pattern、Ontology 或 Grammar 演化先形成可验证 KnowledgeClaim，经 provenance、counterevidence、scope 和 governance gate 后方可晋升；知识成熟度与 production activation 严格分离。所有长期反馈必须产生新版本而不是原地改写，因此整个系统既能形成 Design Production、Human Collaboration、ARSO Optimization 和 Knowledge Evolution 四个闭环，又不会形成循环对象所有权、自我确认评价或未经证据治理的长期知识污染。**

## V5.0 Master Freeze 判定

这次统一以后，我认为 **Design Intelligence 已经不需要继续增加 B09/B10 级别的顶层规范**。

当前可以正式判定：

$$
\boxed{
DI\ V5.0
\ Application\ Architecture
=
FROZEN
}
$$

而接下来真正应该进入的不是继续写架构，而是 **Engineering Implementation Contract**。最合理的下一步是：

$$
\boxed{
DI\text{-}E01
\;|\;
Canonical\ Data\ Model
+
Pydantic\ Schema
+
Object\ Registry
+
Version/Reference\ Contract
}
$$

先把今天已经冻结的 `StyleBrief → DesignDecision → DesignRoute → DesignSpec → GenerationPackage → Evaluation → Evidence → Diagnosis → Intervention → Knowledge` 变成**真正可编码的 V1 数据模型**。这一步完成以后，Design Intelligence 才从“完整架构规范”真正进入可执行系统。
